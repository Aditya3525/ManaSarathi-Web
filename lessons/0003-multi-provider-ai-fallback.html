Lesson 3: The Multi-Provider AI Fallback System

Welcome to Lesson 3! One of the most impressive parts of ManaSarathi is its resilient AI layer. Examiners love to ask: "What happens if OpenAI's servers go down? Does your chatbot crash?"

In this lesson, we will learn how you built a custom failsafe fallback chain that guarantees 100% uptime.

1. The Core AI Provider Interface

To avoid coupling the code to just one provider (like OpenAI), you wrote a generic interface. Any AI service must implement the same interface. In llmProvider.ts:

interface AIProvider {
  generateResponse(messages: AIMessage[]): Promise;
  isAvailable(): Promise;
}

2. The Priority Fallback Chain

When the user sends a message, the server runs down a prioritized list of AI providers. If one fails, it instantly falls back to the next one:

[User sends chat]
      ↓
[1. OpenAI] ── (Failed or in cooldown?) ──→ [2. Anthropic]
                                                   ↓ (Failed?)
[4. NVIDIA] ←── (Failed?) ── [3. Gemini] ←─────────┘
      ↓
[5. HuggingFace] ── (Failed?) ──→ [6. Ollama (Local Fallback)]

This fallback priority chain is configured dynamically in your environment variables.

3. Failsafe Features (The Examiner-Wow Factor)

A. Circuit Breaker / Cooldown

If a provider fails **10 times in a row**, the server flags it as "unhealthy" and puts it on a **3-minute cooldown**. During this cooldown, the server doesn't even try to call it, saving time and keeping response times fast for the user.

B. Key Rotation

What if you run out of API credits or hit rate limits? Your backend allows registering multiple API keys per provider (e.g. OPENAI_API_KEY_1, OPENAI_API_KEY_2). The system automatically rotates through them if one returns a rate-limit error.

C. Local Ollama Fallback

In development mode, if all internet-based API providers fail (or if you have no internet access), the system falls back to a locally hosted LLM running on **Ollama** (e.g., Llama 3). This ensures the app is always functional.

💡 Examiner Tip: If the examiner asks, "Why did you build this complex fallback system instead of just calling OpenAI?", your answer should be: "Production mental wellness applications require high availability. Relying on a single API provider creates a single point of failure (SPOF). This multi-provider fallback architecture ensures that if one provider experiences an outage, rate limits, or network errors, the system gracefully degrades to alternative providers without interrupting the user's therapy support session."

🧠 Active Recall Practice (Desirable Difficulty)

Question 1: The Circuit Breaker

Describe what happens when a provider fails 10 consecutive times.

Answer: It enters a 3-minute cooldown period. During this time, the `LLMService` skips it entirely in the priority list to prevent slow request timeouts and immediately queries the next active provider in the chain.

Question 2: Decoupled Design

Why did we create an `AIProvider` interface instead of writing provider-specific code directly in our chat controllers?

Answer: It decouples our core chat logic from individual API SDKs. If we want to add a new AI provider in the future, we only have to write a new class implementing the `AIProvider` interface, without modifying the controller or routing logic.
