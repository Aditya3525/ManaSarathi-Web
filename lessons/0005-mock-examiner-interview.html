🎯 The Mock Viva

Q1: Architecture "Explain the flow of a request in your system when a user logs a mood."

Ideal Answer Blueprint:

"When the user logs a mood, the frontend sends an HTTP POST request to /api/mood. The request first passes through Express global middleware (such as Helmet, CORS, and rate limiters) to verify the source and protect server resources. Next, our JWT authentication middleware intercepts the header, decodes the token, and attaches the authenticated user object to the request. The router maps the request to the mood controller, which validates the inputs using a Joi/Zod schema. Finally, the controller calls Prisma ORM to insert the record into PostgreSQL and returns a 201 Created response."

Q2: Security "If I steal a user's JWT, can I access their account forever? How does your system mitigate this?"

Ideal Answer Blueprint:

"No, you cannot. Our JWT tokens are short-lived to minimize the security impact of a stolen token. However, to keep the user experience seamless, we built a custom auto-refresh middleware. If a user makes an API request and their token is near expiry, the server automatically issues a new JWT token in the X-New-Token response header. The frontend automatically switches to the new token, so active users are never logged out, but idle tokens expire quickly."

Q3: DB Modeling "How do you define a one-to-many relationship in your Prisma schema?"

Ideal Answer Blueprint:

"In our schema.prisma file, we define it by declaring a list array of child records on the parent model (for example, moodEntries MoodEntry[] on the User model). In the child model (MoodEntry), we specify a foreign key field referencing the parent model's ID, mapped via the @relation attribute. When Prisma client generates types, it handles database joins automatically."

Q4: AI Logic "Why did you build a fallback chain instead of sticking to a single model provider?"

Ideal Answer Blueprint:

"ManaSarathi is a mental wellness support platform, so high availability is critical. Relying on a single API provider (like OpenAI) creates a single point of failure. If they face an outage, rate limit, or network latency, our service goes down. We created a decoupled AIProvider interface and built an automated fallback chain (OpenAI → Anthropic → Gemini → NVIDIA → HuggingFace → Ollama). If one provider fails, the system immediately cascades to the next healthy provider."

Q5: Fail-Safe "What is the circuit breaker/cooldown mechanism in your AI service?"

Ideal Answer Blueprint:

"If an AI provider fails 10 times consecutively, we don't want to keep calling it and wasting time on network timeouts. The system trips a circuit breaker and puts that provider on a 3-minute cooldown. During this cooldown, the provider is bypassed entirely, ensuring fast response times. After 3 minutes, it is tested again to see if it has recovered."

Q6: Security Checks "How do you protect your app against XSS (Cross-Site Scripting) and SQL Injection?"

Ideal Answer Blueprint:

"For SQL Injection, our use of Prisma ORM prevents it naturally because Prisma converts queries into parameterized statements, ensuring user input is never interpreted as executable SQL. For XSS, we sanitise all request bodies using custom sanitization middleware (stripping out illegal script/HTML tags) and use Helmet CSP headers to prevent browsers from executing untrusted scripts."
